## Decisión de arquitectura para esta tanda

La implementación propuesta usa un target estático opcional de NSC que enlaza las bibliotecas oficiales de Clang 23.1.0 y crea una sesión administrada por cada compilación/configuración pertinente. NSC sigue siendo dueño de la compilación del programa; Clang es el frontend que interpretará las declaraciones C/C++. La sesión se prepara en esta tanda y no se afirma que ya resuelva llamadas a bibliotecas. No se añade un modo nuevo al ejecutable Clang ni se modifica su código fuente para esta integración inicial.

Hay dos niveles independientes de activación: la opción de CMake habilita que el binario contenga el componente; una configuración explícita de sesión solicita usarlo en una compilación o prueba concreta. Un binario construido con el componente, pero sin configuración de sesión, debe seguir la ruta NS ordinaria. El mecanismo público para declarar headers y bibliotecas pertenece a la tanda siguiente; no introducir un formato de proyecto ni un flag de usuario que parezca importar bibliotecas antes de que exista esa capacidad.

### Mapa de dependencias entre los archivos propuestos

`CppSessionOptions.h` y `CppSessionDiagnostic.h` contienen solo tipos de valor estándar; `CppInteropSession.h` y `CppInteropSessionFactory.h` dependen de esos contratos y no incluyen cabeceras Clang. `ProjectCompilation` consume la interfaz, no la clase concreta. `ClangSession`, `ClangSessionAction`, `ClangInvocationBuilder` y `ClangDiagnosticConsumer` viven en `nsc_cpp_interop` y pueden incluir Clang. `CppDiagnosticAdapter` consume los valores en el frontend y conoce `SourceManager` y diagnósticos NS. La composición del driver decide si proveer la factory; el flujo ordinario no la necesita. Las consultas semánticas y CodeGen de C++ aún no forman parte de esta interfaz inicial.

Los tests de inyección usan una implementación falsa de la interfaz y sus propios contadores poseídos, sin llamar a Clang. Los tests de sesión real enlazan `nsc_cpp_interop` solo en modo `ON`. La prueba de un cliente independiente de `nsc_frontend` comprueba que el grafo de `OFF` no requiere symbols ni archivos de Clang. Si un target exportado en `ON` incorpora el componente concreto, sus dependencias transitivas y exportación deben quedar explícitas; no resolver un ciclo agregando todas las bibliotecas a todos los targets.

## Contratos de las clases nuevas

### Configuración y resultado

`CppSessionOptions` distingue la identidad y ruta de referencia del driver de Clang, el triple de target, modo C o C++, estándar explícito, directorio de recursos, directorio de trabajo y secuencias ordenadas de rutas y macros. La integración propuesta usa bibliotecas Clang enlazadas: **no requiere ejecutar un `clang.exe` externo para cada sesión**. Una ruta de referencia puede servir al driver para localizar recursos, pero con recursos configurados explícitamente no se debe convertir la presencia de un ejecutable independiente en requisito sin evidencia. No convierte una ruta vacía en una búsqueda silenciosa de otra instalación. Para esta primera implementación, la configuración de prueba debe coincidir con Windows x64 de `TargetInfo::WindowsX64()`; esa clase devuelve el triple Windows MSVC (`src/Target/TargetInfo.cpp:82-85`). Esta elección describe el ABI inicial, no exige desplegar Visual Studio en el destino.

`CppSessionOpenResult` debe ser representable en C++20 y expresar una alternativa exclusiva: sesión válida o error estructurado. Puede implementarse con un struct y `unique_ptr`, sin depender de `std::expected` de C++23. Un error conserva fase, diagnóstico y configuración relevante. No convertir advertencias en éxito si hubo errores. No hacer que los strings o rutas recibidos como `string_view` dependan del objeto de opciones de un llamador que ya terminó.

**Interfaz propuesta a nivel de firma** — nombres diseñados para esta implementación, no símbolos existentes:

```cpp
class CppInteropSession {
public:
    virtual ~CppInteropSession() = default;
    virtual CppSessionState state() const noexcept = 0;
    virtual std::vector<CppSessionDiagnostic> diagnosticsSnapshot() const = 0;
    virtual CppSessionCloseResult close() = 0;
};

class CppInteropSessionFactory {
public:
    virtual ~CppInteropSessionFactory() = default;
    virtual CppSessionOpenResult open(CppSessionOptions options,
                                      CppCancellationToken cancellation) = 0;
};
```

`CppSessionState`, `CppSessionCloseResult`, `CppSessionOpenResult` y `CppCancellationToken` se definirán en los headers propios del componente con valores poseídos y estados documentados. `close()` puede devolver un resultado para no ocultar errores; el destructor no propaga excepciones y realiza limpieza de respaldo. El token debe tener semántica de copia y vida claramente poseída, no capturar un objeto de stack cuyo dueño pueda terminar antes que la sesión. Los accessors devuelven copias o valores de lifetime comprobado. Esta interfaz no expone aún operaciones para resolver tipos, instanciar templates ni invocar C++; se extenderá cuando se diseñen esas tandas.

La primera tanda necesita una unidad fuente de prueba y sus opciones para inicializar y observar una sesión; usar un archivo o buffer temporal aislado en A: durante las pruebas futuras. No introducir aún una sintaxis pública de importación. Las funciones `CppInteropSession::state`, `diagnostics`, `close` y `CppInteropSessionFactory::open` son nombres propuestos. `close` es idempotente; una sesión cerrada no presta más acceso al contexto y su destructor llama cierre como respaldo. Si los diagnósticos deben consultarse después de cerrar, copiarlos a un valor del propietario antes del cierre y definir esa vida en la interfaz.

Revisar las opciones concretas que el driver construya, incluyendo módulos, PCH y reportes. Esta restricción de las pruebas no excluye módulos C++ del objetivo posterior.

### Construcción de la invocación

`ClangInvocationBuilder::build` recibe opciones validadas y devuelve una invocación propia o diagnóstico. Propuesta de secuencia: (1) validar versión, triple y rutas fijadas; (2) construir argumentos de driver para una sola unidad con modo C/C++ explícito; (3) obtener la configuración de frontend con las reglas de Clang y conservar valores necesarios; (4) comprobar target y directorio de recursos resultantes antes de iniciar la acción; (5) conservar la identidad de esa configuración mientras la sesión esté viva. No convertir directamente argumentos de usuario de driver en argumentos `cc1` sin pasar por la transformación correcta.

La evidencia concreta es `clang/lib/Tooling/Tooling.cpp:132-179,406-425`: Clang forma una `Compilation`, selecciona un job de frontend y llama `CompilerInvocation::CreateFromArgs`. `getCC1Arguments` en ese archivo es una función de implementación, no asumir que puede llamarse como API pública. El plan de implementación debe reproducir esa selección usando APIs expuestas o elegir otro mecanismo de Clang que permita mantener la sesión viva; si hay cero o varios jobs, informar el resultado en lugar de elegir uno arbitrariamente. Tratar los strings de argumentos como propietarios mientras Clang los consuma. La equivalencia exacta de la invocación y los headers se validará con la herramienta fijada, no se da por demostrada.

### Apertura, cierre y concurrencia

`ClangSession::open` crea el consumidor de diagnósticos, la invocación, `CompilerInstance`, gestores de archivos/fuente y target; inicia una acción frontend apropiada y conserva todo lo que se necesita hasta cerrar. El orden definitivo debe seguir las precondiciones de `CompilerInstance.h:227-254` y `FrontendAction.h:229-249`; la implementación no debe llamar `ExecuteAction` después de haber inicializado objetos que esa API exige aún no inicializados. Debe tratar explícitamente `PrepareForExecution`, preparación de la acción y target si elige administrar la acción manualmente; no mezclar dos caminos de inicialización.

Para esta tanda, `ClangSessionAction` debe permitir analizar una unidad C o C++ de control y mantener `ASTContext` y `Sema` accesibles **dentro del componente** hasta `close`. La primera comprobación de vida consiste en consultar desde el componente una propiedad o declaración de la unidad después del parseo y antes del cierre, y asegurar que ya no se permite acceso tras el cierre. El uso ordinario de `ASTFrontendAction` termina el parseo mediante `ParseAST` (`FrontendAction.cpp:1441-1465`); mantener la acción abierta puede conservar el contexto, pero **no demuestra que pueda seguir aceptando todas las demandas e instanciaciones posteriores**. La estrategia de parseo incremental, módulos y especialización por demanda se valida en la tanda correspondiente; no prometerla solo por conservar punteros. Si para la vida mínima no es viable esa acción, escoger y documentar una alternativa oficial observando sus precondiciones.

`FrontendAction::BeginSourceFile` indica que si falla no debe llamarse `EndSourceFile`; si tiene éxito, la sesión registra que existe un cierre pendiente. Al cerrar, detiene nuevas consultas, espera el trabajo que use la sesión, recoge diagnósticos, llama `EndSourceFile` exactamente una vez cuando corresponda y destruye acción e instancia con el orden verificado. `FrontendAction.cpp:1366-1393` muestra que el cierre libera Sema y AST. Carbon mantiene un parser y una acción personalizados (`generate_ast.cpp:848-925,995-1037`); es un ejemplo para estudiar, no se copia su flujo inverso ni se garantiza que un `SyntaxOnlyAction` cerrado conserve el contexto. No llamar `llvm_shutdown` por cada sesión: es global, y su ubicación correcta debe resolverse a nivel del proceso y comprobarse con los demás usuarios LLVM.

No determinar éxito solo por el valor de `FrontendAction::Execute()`: la implementación observada (`FrontendAction.cpp:1342-1364`) puede devolver `llvm::Error::success()` después de `ExecuteAction`, mientras los errores de lenguaje se reflejan en el motor de diagnósticos. Comprobar tanto el error devuelto como `DiagnosticsEngine::hasErrorOccurred()` y el estado de la acción; capturar y consumir correctamente `llvm::Error`. La implementación de Clang usa además `assert` para algunas precondiciones internas, por lo que la validación debe impedir invocaciones inválidas antes de llamarlas; no prometer que un `catch` convierta en diagnóstico todos los fallos fatales internos.

No compartir una instancia mutable de Clang entre compilaciones o workers simultáneamente. Empezar con una política de un único ejecutor por sesión y valores de configuración separados; hacer explícito si la factory es segura para abrir sesiones independientes desde varios hilos. En cancelación, no detener de manera asíncrona una operación arbitraria de Clang: rechazar trabajo nuevo, esperar el trabajo vigente y liberar. Las garantías precisas requieren pruebas y no se han medido.

**Estados y pruebas de transición:** la factory construye de forma privada (`creando`), publica solo una sesión `lista` cuando todos sus requisitos pasan y, ante error, entrega datos de fallo sin publicar una sesión incompleta. `close` pasa `lista → cerrando → cerrada`; una segunda llamada con estado `cerrada` no repite la finalización. Si `BeginSourceFile` falló, la marca de inicio permanece falsa y el cleanup no llama `EndSourceFile`; si tuvo éxito, la marca se consume al llamar a `EndSourceFile` una sola vez. El caller recibe un snapshot propio de diagnósticos antes de soltar el `CompilerInstance`. La política de lock/cola para solicitudes concurrentes se debe codificar en el componente; no usar únicamente un estado sin sincronización como si garantizara seguridad entre hilos.

### Diagnósticos sin inventar ubicaciones

`ClangDiagnosticConsumer::HandleDiagnostic` copia severidad, mensaje, identificador disponible, ubicación de spelling/expansión y notas antes de que desaparezca el contexto. La representación de NSC `Diagnostic` tiene su propio `FileId`; se añade un adaptador explícito que registre el buffer correcto en el `SourceManager` NS solo cuando corresponda, manteniendo el texto efectivo de la compilación. No volver a leer del disco un header distinto del buffer o overlay que analizó Clang y atribuirle sus offsets. Para diagnósticos sin ubicación, usar un camino de presentación de integración que no simule un archivo o línea.

**Propiedad concreta recomendada:** `ClangSession` posee el `ClangDiagnosticConsumer`; al crear el motor mediante `CompilerInstance::createDiagnostics`, pasar `ShouldOwnClient=false` y mantener el consumidor vivo hasta que se destruyan tanto la instancia como cualquier referencia compartida al motor. Alternativamente se puede ceder ownership a Clang, pero nunca combinar ambas propiedades. `CompilerInstance.h:714-742` documenta la opción y `clang/lib/Basic/Diagnostic.cpp:101-105` muestra cómo `setClient` administra el dueño. Asegurar que el consumidor no almacene una referencia a un sink NS que ya haya terminado; el snapshot del resultado debe poseer sus mensajes. Probar la destrucción tras fallo parcial, inicio correcto y cierre repetido. El orden concreto de miembros de la implementación se decide junto con el resto de objetos retenidos, no se infiere de un ejemplo de stack diferente.

Esto es necesario porque `src/Diagnostics/DiagnosticRenderer.cpp:17-25` presenta `<source>` y posición por defecto si no encuentra un archivo; por sí solo no expresa fielmente un diagnóstico externo sin ubicación. Proponer `CppDiagnosticAdapter` en `src/Frontend/Interop/CppDiagnosticAdapter.cpp` y una presentación externa separada o extensión explícita del modelo NS, sin alterar salidas ordinarias. El componente Clang produce valores `CppSessionDiagnostic` y no enlaza de vuelta con `nsc_frontend`; el adaptador, ubicado en la capa que ya conoce los diagnósticos NS, consume esos valores.
